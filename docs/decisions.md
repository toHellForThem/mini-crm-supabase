# Решения и допущения

## Что решил сам там, где ТЗ не даёт однозначного ответа

1. **Смена статуса — только через RPC `update_task_status()`, а не через прямой `UPDATE`.**
   ТЗ требует, чтобы запрещённый переход не прошёл даже при ручном запросе. Поэтому поле `status` нельзя менять напрямую: триггер `prevent_direct_status_change` блокирует любое изменение статуса в обход RPC — в том числе для постановщика. RPC проверяет роль, владельца задачи и допустимость перехода, после чего сам пишет историю.

2. **История статусов append-only на уровне прав.**
   У ролей `authenticated` и `anon` отозваны `INSERT/UPDATE/DELETE` на `task_history`. Записи создают только триггеры и `security definer`-функции. Так историю нельзя подделать, изменить или удалить через API.

3. **Создание задачи тоже попадает в историю** как переход `null → Новая` с комментарием «Задача создана». ТЗ говорит про «каждую смену статуса»; создание — это начальный статус, и его полезно видеть в истории.

4. **Новая задача всегда создаётся в статусе «Новая».**
   Триггер `force_new_task_status` не даёт создать задачу сразу в другом статусе, даже если постановщик передаст `status` вручную.

5. **Роль хранится в отдельной таблице `profiles`, связанной с `auth.users`.**
   Supabase Auth не хранит прикладные роли. Профиль создаётся автоматически триггером `handle_new_user`; роль и имя берутся из `user_metadata` при создании пользователя. Если метаданных нет — роль по умолчанию `executor`.

6. **Открытая регистрация отключена.** Пользователей создаёт администратор вручную в Supabase (Authentication → Users). В приложении нет экрана регистрации.

7. **Постановщик видит все профили, исполнитель — только свой и профили участников своих задач.**
   Это нужно, чтобы исполнитель видел имя автора задачи и имя того, кто менял статус, но не видел всю базу сотрудников.

8. **Удаление объекта каскадно удаляет его задачи и их историю** (`ON DELETE CASCADE`). Это ожидаемое поведение для «удалили стройку — удалили всё, что к ней относится».

9. **Редактирование задачи не меняет статус.**
   Форма редактирования меняет только название, описание и исполнителя. Статус меняется отдельными кнопками через RPC.

10. **Интерфейс показывает только доступные действия.** Кнопки «Взять в работу», «На проверку», «Принять», «Вернуть на доработку» рендерятся в зависимости от роли, назначения и текущего статуса. Но это лишь удобство: настоящая проверка — в базе.

11. **Демо-данные (`seed.sql`) временно отключают триггеры**, чтобы создать задачи в разных статусах. Это только для наполнения демо и не используется в рабочем приложении.

12. **UI-библиотека — Tailwind CSS без тяжёлого компонентного фреймворка.**
   ТЗ не оценивает дизайн; выбран минимальный стек, чтобы сосредоточиться на логике и безопасности. Интерфейс аккуратный и понятный, но без сложных компонентов.

13. **Без оптимистичных обновлений.** После мутаций React Query инвалидирует кеш и перезапрашивает данные — так проще гарантировать, что интерфейс показывает состояние из базы, а не предполагаемое.

14. **История пишется в той же транзакции, что и смена статуса.** Если запись истории не удалась, статус тоже не поменяется — данные не разъедутся.

## Что не успел / сознательно не делал

- **Видео-объяснение для руководителя** — вместо него подготовлен текст [`docs/explanation.md`](explanation.md) (полстраницы, без терминов).
- **Деплой** — приложение готово к Vercel, но для запуска нужны URL и anon-ключ вашего Supabase-проекта. Инструкция в README.
- **Управление пользователями из интерфейса** — по ТЗ пользователи создаются вручную в Supabase.
- **Сброс пароля и приглашения** — не входило в минимальные требования.
- **Пагинация, поиск, фильтры** — при 2–3 объектах и нескольких задачах не нужны; при росте добавил бы.
- **Realtime-обновления** — не требовались; данные обновляются при навигации/инвалидации.
- **Аудит изменений полей задачи** (не только статуса) — ТЗ требует историю именно смены статусов.
- **Фронтенд-тесты** — проверена сборка TypeScript; логика безопасности покрыта SQL-тестами.

## Проверено

- `npm run build` — сборка проходит без ошибок TypeScript.
- SQL-тесты в [`tests/sql/rls_test.sql`](../tests/sql/rls_test.sql) на реальном PostgreSQL подтверждают:
  - исполнитель видит только свои задачи и только «свои» объекты;
  - прямой `UPDATE` статуса не проходит (RLS/триггер);
  - запрещённые переходы через RPC отклоняются;
  - возврат на доработку без комментария отклоняется;
  - история недоступна для записи через API;
  - постановщик видит всё и может принимать/возвращать задачи.
